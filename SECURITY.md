# Security review record

This project uses a standard OpenZeppelin ERC-20, an immutable hook, and a one-time hook launcher. The review below is local implementation review, not an independent audit or authorization to deploy. This source repair does not deploy, replace, or mint the token.

## Trust boundaries

- The application factory deploys `DCAHookLauncher` with the requester's explicit owner and canonical manager. The requester configures the existing token and selects the opening price. The launcher alone deploys and initializes its child pool, atomically. The application factory is not the owner. No token mint, allocation, transfer, approval, liquidity custody, or swap entry point exists on the launcher.
- The operator must fund and route to the exact child hook pool. A default guard-only pool or an already initialized unhooked pool does not acquire a fee by deploying this application. Liquidity and routing changes require separate reviewed operator actions and price bounds; the source does not assume an external factory ABI or authorize migrations.
- The hook trusts its immutable PoolManager to implement v4 accounting and report truthful pool deltas. Production must use the documented canonical Ethereum deployment. Constructors deliberately make no external calls, so a mistyped manager or token must be caught by deployment review.
- FWA is the supplied canonical token. Its owner and its own restrictions remain external protocol dependencies. The hook owns claims; successful fee claims rely on the manager being able to transfer FWA to the fixed recipient.
- Traders and routers are untrusted. No sender, router, token holder, or deployer receives a fee exemption. Routers remain responsible for slippage and execution limits.
- `PrepareLaunch` is a read-only simulation tool, never a signer or application owner. It checks Ethereum chain ID, the expected requester owner, canonical manager, DCA metadata and supply, FWA's manager/distributor status, and price bounds before returning activation calldata. These checks are a snapshot and do not establish contract provenance, choose a fair opening price, or prevent later FWA governance changes. Verify the actual deployment records and bytecode before signing.

## Adversarial cases reviewed

| Concern | Mitigation and evidence |
| --- | --- |
| Supply growth or privileged confiscation | Only the constructor reaches `_mint`. ERC-20 admin, pause, blacklist, burn-from, and upgrade probes fail. Factory allocations and ordinary transfers arrive whole. |
| Incorrect currency or changed pool fee | Immutable pool ID includes both ordered currencies, fee, tick spacing, and this hook. Rejection tests cover other keys, zero fee, and the dynamic fee flag. |
| Hook address missing required callbacks | Constructor validates all address flags. Tests mine and deploy real CREATE2 hook addresses and reject mismatches. |
| Ordinary application deployment cannot choose hook flags | The ordinary-address launcher embeds the child creation code and deploys it with an off-chain prepared salt. Tests use a separate factory with plain CREATE, then exercise the production activation path. Permission validation on the child remains enforced. |
| Deployment factory mistakenly owns setup | Constructor requires the explicit requester owner. Tests show the deploying factory and unrelated callers cannot configure or activate. There is no `tx.origin` authority. |
| Missing/stale setup or accidental second deployment | Token-dependent preparation/activation fail while unset. First use requires code on manager/token. Configuration freezes before the manager initialization call; duplicate launch and post-launch token changes fail. All constructor checks work on an empty chain. |
| Bad salt or initialization failure bricks activation | The child deployment, saved hook, and pool initialization share a transaction. Invalid-salt and invalid-price tests assert no surviving child/pool and successful retry. Preparation hashes the creation code in the deployed launcher. |
| Token setting changes between preparation and submission | `launchWithToken` includes the token, salt, and opening price in the owner's signed call, sets the token, and activates atomically. A prior setting cannot change that call's token. Failed activation restores the prior setting; the legacy two-step path remains available. |
| Prepared transaction points at the wrong pool | Tests execute the exact returned calldata and compare its predicted hook, complete sorted pool key, pool ID, price, and retained platform fee to the real manager. Both address orderings then buy, sell, and claim through that pool. |
| Initialization front-running | `beforeInitialize` authenticates the manager and the deploying factory. Unauthorized initialization reverts before pool creation. |
| Callback spoofing or arbitrary payout recipient | All active callbacks require the manager. The unlock callback additionally requires an in-progress claim; it ignores externally supplied destination data. Recipient is a constant. |
| FWA transfer restriction | Swaps mint claims rather than transferring FWA out of the manager. Claim burns them and uses manager-to-recipient `take`. The mock rejects ordinary transfers. |
| First-swap reserve shortage | Claim minting needs no pre-existing liquid FWA withdrawal. A single-sided launch test buys and sells with less than the fee in pre-swap manager reserves. |
| Wrong signs or charging DCA | Tests compare real swaps with a control pool for both sort orders and every exact-input/output mode. Only the FWA delta changes. |
| Fee on unfilled input/output | FWA-specified partial fills revert atomically. Other partial fills tax actual FWA deltas only. Pool price, balances, and fee claims roll back on failures. |
| Rounding and overflow | Integer 5% fee rounds down. Net-to-gross inversion is fuzzed for exactness and minimality. Signed ranges are checked before negation/gross-up. Aggregate claims redeem in bounded chunks. |
| Fee theft using claims | The hook never grants ERC-6909 allowance or operator rights; attempts to transfer its claims fail. Donated FWA claims can only reach the fixed recipient. |
| Reentrant or failed claim | `nonReentrant`, authenticated callback, and state cleared before burn/take. An adversarial FWA mock attempts reentry; failed payout leaves all claims recoverable. |
| Unsettled flash accounting | Real-manager integration and stateful tests check zero remaining deltas and a locked manager after every transaction. |
| Multiple swaps in an unlock | No global per-swap temporary state; each fee follows its callback's parameters/deltas. Batch and randomized sequence tests pass. |

The hook has no swap entry point, so Uniswap's hook self-call exemption cannot be used to bypass its fee. PoolManager `mint` does not invoke token or recipient callbacks. The only external ERC-20 payout happens under the claim guard. The launcher's child constructor makes no external calls, and the launcher stores the child (freezing setup) before calling the trusted manager. There is no arbitrary call/delegatecall or asset withdrawal on the launcher. Its owner can select a wrong token or opening price before activation; review those values. A lost setup key has no recovery path, and successful activation cannot be undone.

## Validation and limits

The delivered tests include deterministic success/failure tests, parameter fuzzing, and stateful conservation invariants against the real vendored PoolManager. The shared hook harness uses the new launcher for both currency orderings, including all four swap modes and failed-payout/partial-fill checks. Dedicated launcher tests also prove that an existing unhooked pool remains distinct, preventing a false claim that this repair retrofits it. Default fuzzing uses 256 cases per property; the basic fee invariant suites run 128 sequences of 32 calls. Additional stateful suites and arithmetic fuzz counts are described in `test/ADVERSARIAL_TESTS.md`. The test harness is deterministic from its seed, independent of caller identity/environment, and contains no live network calls.

The follow-up adds atomic configuration/activation and tests the preparation script directly, including incorrect owner/chain/manager, absent code, token metadata/supply mismatches, incompatible FWA settings, an occupied hook address, exhausted mining, and already completed activation. Its integration fixture runs the real PoolManager constructor at the canonical test address and installs the returned runtime, preserving the manager's immutable anti-delegatecall address. The restricted FWA fixture adds only the metadata/configuration views needed by the preflight. It is not a live mainnet fork. The returned activation calldata is submitted locally by an explicit test owner; the test then proves unchanged DCA supply and fee payout conservation, including failed payout and retry.

Separate read-only RPC observations at Ethereum block 26178567 verified the FWA symbol, decimals, canonical manager, and active manager distributor registration. They are recorded in the README as integration evidence, not as proof that DCA or its hooked pool is deployed. No signer, key, transaction submission, or deployment manifest was used.

Compiler/Foundry checks: `forge build`, `forge test`, and `forge fmt --check`. Runtime-size checks cover the token, hook, and launcher; prohibited-opcode checks cover the token and hook. Deployment preparation functions are executed directly in tests, including the empty-chain constructor path and configured-launcher path. These local checks do not substitute for the independent verifier.

Slither and Mythril were not run. Foundry lint's signed-cast warnings are reviewed against explicit sign/range checks; the claim's external calls are protected by OpenZeppelin's reentrancy guard and PoolManager authentication. The launcher emits its success event after initialization, with configuration already frozen; it intentionally ignores the returned initial tick because its public result is the child hook and the manager records the pool state. Tests do not prove behavior of arbitrary future FWA implementations, liquidity availability, router integrations, or correct external manifest wiring. An independent contributor should review those boundaries and the exact deployment artifacts before release.
